# AI 产品架构逆向分析

以“可复核页面证据”为唯一事实基础，逐层还原用户经历、Agent 协作、工具执行、全局上下文、资产与模型架构。不要把产品口头回复、模型隐藏思维、题目模板或常见后端方案写成已确认事实。

## 开始前

1. 读取用户指定的文件、文件夹、页面和已有分析材料。
2. 若输入是截图文件夹，先运行：

```bash
python3 scripts/inventory_screenshots.py <截图目录> --output <证据清单.csv>
```

3. 读取 [references/evidence-protocol.md](references/evidence-protocol.md)，建立证据编号与安全边界。
4. 根据用户目标，按需读取：
   - 用户旅程、Agent 契约、System Prompt、HTML 交付：
     [references/deliverable-specs.md](references/deliverable-specs.md)
   - 分层架构、全局上下文、数据实体、风险与 To-Be：
     [references/architecture-schema.md](references/architecture-schema.md)
5. 若已有前序产物，复用其证据编号，但回查原始页面或截图；前序结论不是新的页面证据。

## 证据等级

始终使用且仅使用以下四类标签：

- 【已确认】：页面、官方资料或可复核工具结果直接支持。
- 【合理推断】：多条行为事实支持，但后台实现不可见。
- 【建议设计】：为稳定性、可恢复性或治理补充的方案。
- 【未知】：当前证据不足。

用户只要求用户旅程时，可按其指定标签映射为【页面事实】、【合理推断】、【尚未确认】；不要同时混用两套标签。

## 核心工作流

### 1. 建立查看范围

- 按时间顺序列出全部截图、页面、聊天和资产视图。
- 记录未访问、模糊、截断、非同一时刻或无法确认的内容。
- 不读取 Cookie、Token、密码、鉴权头或个人敏感信息。
- 浏览器只读；除非用户另行明确授权，不点击生成、重试、发布、删除、购买、充值或覆盖资产。

### 2. 先还原用户旅程

- 从最早用户输入开始，记录需求、剧本、风格、参考资料、表单选择和确认。
- 同时检查聊天、按钮、表单、画布节点、资产卡、历史、任务状态、错误、预览与剪辑入口。
- 对每一步记录：用户目标、动作、页面反馈、决策、资产/状态变化、阻力和证据。
- 必须覆盖正常、修改/纠偏、失败/中断三类路径；无失败样本时保留为【未知】，不要编造产品处理方式。
- Agent 说“已完成”时，检查真实资产、状态和预览；冲突并列记录。

### 3. 识别实际 Agent

- 只记录页面有证据支持的 Agent，不预设数量。
- 对每个 Agent 记录：加入时机、触发者、上游、下游、再次调用、缺席步骤和能力边界。
- 名称未完整显示时，用“功能阶段 Agent”，并把推测名称标为【合理推断】。
- 不把公开的“思考完成/规划完成”还原为隐藏思维链。

### 4. 建立 Agent I/O 契约

逐一检查六类输入：

1. 用户当前输入
2. 用户长期信息
3. 项目全局上下文
4. 上游 Agent 输出
5. 平台公共资产、知识和规则
6. 工具或运行时结果

逐一检查五类输出：

1. 用户回复
2. 页面组件
3. 文字、图片、视频、音频资产
4. 全局上下文写入与状态
5. 下游任务与交接包

工具名不可见时，使用功能名并注明“功能命名，非官方工具名”。口头计划不等于已执行；只有资产、状态、工具结果或页面变化才能确认执行。

### 5. 还原数据生产者—消费者

- 为每个字段和资产记录生产者、消费者、写入时机、确认门、版本和证据。
- 重点寻找剧本→角色/场景/道具→分镜→视频的引用关系。
- 检查修改上游内容后，下游是否自动失效或重算。
- 标记只写不读、只读不写、聊天/画布/任务/资产库不一致和“口头完成但状态未更新”。

### 6. 按需编写单 Agent 功能等价 System Prompt

- 先完成边界、输入、输出、工具、状态机和规则—证据追溯，再写 Prompt。
- 明确它不是官方原文，只复现可观察行为。
- 把页面事实转换为【事实规则】，必要补充标为【推断规则】，改进项标为【建议规则】。
- 用尖括号占位功能工具，例如 `<生成角色主图工具>`；不要伪造 API 名。
- 完成条件不得只依赖 Agent 自述，至少检查资产存在、上下文写入、验证、用户确认和交接数据。

### 7. 建立完整产品架构

- 同时展示用户交互流、Agent 控制流、工具调用流、上下文流和媒体资产流。
- 拆分用户/渠道、工作台、应用、Agent 编排、工具服务、模型路由、上下文数据、知识资产、基础设施治理九层。
- 把全局上下文拆成语义对象，不画成一个大框。
- 仅把页面出现的模型和参数写成【已确认】；完整动态路由只能是推断或建议。
- 对数据库、队列、云、语言和厂商，只写所需能力、可能类别、推荐方案与不可确认原因。
- 输出 As-Is 与 To-Be，优先补充统一状态事实源、完成门、依赖失效、版本、幂等、额度冻结、安全、追踪和质量评测。

### 8. 生成 HTML 交付

- 先使用 `assets/report-template.html` 作为结构与证据配色参考。
- 让主图、泳道、分层图、时序和风险图承担主要信息；不要把整页做成数据卡片堆叠。
- 表格只用于精确追溯和契约字段。
- 每个关键节点标证据编号；提供 Mermaid 源码时同时给出可读的静态结构或降级展示。
- 若用户要求只要 HTML 地址，把全部说明收录到 HTML，聊天只返回文件链接。
- 运行：

```bash
python3 scripts/validate_analysis.py <报告.html>
```

修复缺失章节、证据标签、重复 ID 或越界表述后再交付。

## 质量门

交付前逐项确认：

- 时间线从最早一条用户输入开始。
- 每个已确认结论可回到页面原文、按钮、Agent、资产、错误或截图编号。
- 没有把 Agent 的计划、营销文案或隐藏思维写成工具事实。
- 没有把建议架构写成当前架构。
- 聊天、任务、画布、资产和最终预览冲突被明确保留。
- 失败、余额不足、安全、中断、重试和版本在无样本时保持【未知】。
- 工具名和字段名的官方性边界清楚。
- 敏感信息、凭证和无授权私有资产未进入报告。

## GitHub 发布边界

- 默认发布通用方法、模板和匿名化示例，不提交用户截图、账号信息、Token、Cookie、原始私有对话或未经授权的产品资产。
- 发布前检查 `git status`、`.gitignore`、目标仓库和 `git remote -v`。
- 未明确仓库可见性时，先发布为私有仓库或向用户确认；公开发布前确认授权和许可。
